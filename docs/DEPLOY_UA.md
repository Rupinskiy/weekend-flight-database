# Повне розгортання у GitHub і Cloudflare без Python та командного рядка

**Мета:** відкрити адресу `https://weekend-flight-database.<your-subdomain>.workers.dev`, увійти, додати API-ключі з браузера й натиснути «Зібрати».

## Етап A. Створення GitHub-репозиторію (GitHub Desktop)

1. Завантажте архів v8, розпакуйте в тимчасову папку Windows Explorer. Усередині є `src`, `public`, `tests`, `.github`, `docs`, `wrangler.jsonc`, `package.json`.
2. Запустіть **GitHub Desktop** під вашим акаунтом.
3. Меню **File → New repository**. Назва: `weekend-flight-database`, локальний шлях довільний, Description: `Weekend flight schedules, calendar & fares`. Натисніть **Create repository**.
4. Відкрийте через **Repository → Show in Explorer** створену порожню папку.
5. Скопіюйте **всі розпаковані файли і папки всередину цієї папки**, а не тільки ZIP. Переконайтеся, що Windows скопіював також приховану `.github` і `.gitignore`. **Не копіюйте** чужу `.git` папку, якщо вона є.
6. Поверніться до GitHub Desktop: перегляньте **Changes**, у Summary введіть `Initial import: web-first v8`, натисніть **Commit to main**.
7. Натисніть **Publish repository**, **зніміть галочку Keep this code private** (тобто оберіть Public), опублікуйте.
8. Перевірте репозиторій у браузері: мають відображатися `src/worker.mjs`, `public/index.html`, `wrangler.jsonc` та **Actions → CI**.

**Важливо:** підключений GitHub-конектор дозволяє працювати з уже існуючими репозиторіями, але в поточному наборі дій відсутня операція створення нового репозиторію. Одноразове створення через GitHub Desktop потрібне. Після цього зміни можна робити Pull Requests, не переносити вручну повні ZIP щоразу.

## Етап B. Обліковий запис і D1 у Cloudflare

1. Відкрийте https://dash.cloudflare.com/ і увійдіть або створіть безкоштовний акаунт.
2. У Cloudflare Dashboard знайдіть **Storage & Databases → D1** (розділ може називатися **D1 SQL Database**).
3. Натисніть **Create database**. Назва: `weekend-flight-database`. Оберіть найближче розміщення, якщо Cloudflare пропонує вибір, і створіть.
4. Відкрийте створену базу та скопіюйте її **Database ID (UUID)**. Це не секретний API-ключ, але потрібен для прив'язки.
5. Відкрийте свій GitHub-репозиторій у браузері, файл `wrangler.jsonc`, натисніть **Edit this file** (іконка олівця).
6. Знайдіть рядок `"database_id": "REPLACE_WITH_YOUR_CLOUDFLARE_D1_DATABASE_ID"`. Вставте замість тексту справжній D1 Database ID, не чіпаючи решту файлу.
7. Натисніть **Commit changes** безпосередньо в `main`. GitHub Desktop після цього може зробити **Fetch origin → Pull origin**, щоб синхронізувати локальну копію.

**Не вводьте секретні ключі в `wrangler.jsonc` або будь-який файл GitHub.** Публічний репозиторій індексується і не повинен містити жодного секрету. Секрети вводяться лише через Cloudflare Variables and Secrets або через авторизовану панель.

## Етап C. Прив'язка GitHub до Cloudflare Worker

1. Cloudflare Dashboard → **Workers & Pages → Create application / Create Worker**.
2. Оберіть **Import repository / Connect Git** (назви пунктів відрізняються між версіями інтерфейсу).
3. Дозвольте Cloudflare доступ **лише до нового репозиторію**, якщо пропонується scoped installation.
4. Виберіть `weekend-flight-database`, branch `main`.
5. Build command: `npm install --no-audit --no-fund` (це виконується на хмарному сервері; на вашому ПК нічого не встановлюється).
6. Deploy command: `npx wrangler deploy`.
7. Root directory: `/` (корінь репозиторію). Configuration file: `wrangler.jsonc`, якщо питають.
8. Натисніть **Save and Deploy**. Дочекайтеся статусу **Success**; відкрийте лог, якщо він показує Error.
9. Якщо D1 binding не з'явився, перевірте `database_id` та створення бази; `wrangler.jsonc` має binding із назвою **DB**.

Підключений GitHub → кожний новий merge/push до `main` → автоматичне розгортання через Cloudflare Workers Builds.

## Етап D. Обов'язкові серверні секрети

1. Відкрийте Cloudflare → ваш Worker → **Settings → Variables and Secrets**.
2. Додайте **Secret**, а не відкриту звичайну variable, із назвою `ADMIN_PASSWORD`. Значення — довгий унікальний пароль, збережіть у менеджері паролів.
3. Додайте другий **Secret** із назвою `SESSION_SECRET` — інша випадкова довга фраза, мінімум 32 символи.
4. Додайте третій **Secret** `ENCRYPTION_SECRET` — ще одна **відмінна** випадкова довга фраза, мінімум 32 символи. **Зберігайте її резервну копію в менеджері паролів**: без цього значення вже зашифровані API-ключі не відновляться.
5. Збережіть зміни та, якщо потрібно, зробіть redeploy у панелі. Не додавайте ці секрети у GitHub Actions і тим більше в JavaScript фронтенду.
6. Опційно налаштуйте **Cloudflare Access** для доступу тільки вашої сім'ї. Продукт має також власний пароль входу.

## Етап E. Перший вхід

1. Знайдіть URL Worker (Cloudflare показує `*.workers.dev`).
2. Відкрийте URL. Побачите сторінку входу.
3. Введіть `ADMIN_PASSWORD` (створений на попередньому етапі).
4. Після успішного входу Worker **автоматично ініціалізує SQL-таблиці** в D1; вручну виконувати SQL не потрібно.
5. У вкладці **«Огляд»** перевірте 0 графіків, 0 датованих винятків і 0 API-профілів — це нормальний стан чистої бази.

## Етап F. Внесення ключів в одну панель

1. Вкладка **«API-ключі» → «Додати API-ключ»**.
2. Виберіть `airlabs`, введіть власника, тариф, загальний ліміт за поточний період, сам ключ. Підтвердіть, що власник дозволив використання.
3. За потреби додайте інший ключ AirLabs для іншого власника. Система зможе вибрати активний профіль із залишком бюджету; якщо провайдер встановлює сукупний ліміт, обов'язково заповніть спільну `quota_group` і `group_limit`.
4. Для OAG додайте `oag` із subscription key, а для підписаного HTTP Push — окремий тип `oag_webhook`, де ключ повинен починатися з `whsec_`. Якщо trial закінчується, заповніть поле **Кінець доступу**.
5. Для AeroDataBox додайте тип `aerodatabox`, у полі plan зазначте `rapidapi`, `apimarket` або `direct`, і реальну квоту в units. Для SerpApi — тип `serpapi`.
6. **Заміна:** кнопка «Замінити» біля профілю. **Вимкнення:** кнопка «Вимкнути». **Нова квота:** лише якщо період справді поновився у постачальника.

**Не треба вводити ключі в `.env`.** Це вебпроєкт, а не локальна Python-програма.

## Етап G. Перший збір реальних розкладів

1. Вкладка **«Збір даних»**; залиште або відредагуйте аеропорти `LHR,LGW,STN,LTN,LCY,SEN,BRS,BHX,MAN,LPL,EMA,BOH,SOU,NWI,CWL`.
2. Натисніть **«Створити чергу»**. З'явиться по одному завданню departures і arrivals на аеропорт.
3. Натисніть **«Зібрати наступну сторінку»**. Програма використає одну сторінку AirLabs Routes (до 15 записів у Free-оптимізованому режимі v8.1). Отримані записи проходять окрему стадію COMMITTING невеликими пакетами і спише локальну квоту.
4. Перевірте результат та статус. Для продовження натисніть **«Серія: 5 сторінок»** або залиште Cron виконувати чергу поступово. У статусі COMMITTING здійснюється запис накопичених рядків без нового звернення до авіаційного API.
5. Вкладка **«Авіарозклади»** показує повний каталог, у тому числі рейси поза weekend-вікнами. Можна обирати аеропорти, авіакомпанії, дні тижня, експортувати весь каталог по сторінках.
6. Якщо AirLabs повернув 403/помилку тарифу — він не включений у ваш ключ. Не продовжуйте повторювати платні спроби; відкрийте docs/API_ACCESS_UA.md.

## Етап H. OAG Schedules для сезонних періодів

1. Переконайтеся у кабінеті OAG, що активний **Schedules API**, а не лише Flight Info Alerts.
2. У вкладці **«OAG Delta»** є форма «OAG Schedules — прямий API-збір». Виберіть 1–2 аеропорти та невеликий date range (спочатку ≤30 днів).
3. Натисніть «Поставити в чергу», потім «Зібрати наступну сторінку». Відповідь OAG ставиться у staging і записується невеликими пачками; COMMITTING не витрачає нового OAG API-запиту. Реалізований endpoint `https://api.oag.com/schedules` із параметрами `DepartureAirport`/`ArrivalAirport`, `DepartureDate=from/to`, `CodeType=IATA`, `Limit=100`, `version=v1`.
4. Перевірте фактичні права і формат відповіді вашого ключа. Якщо повернув 401/403 або змінився формат контракту, зупиніться й збережіть код помилки (не сам API-ключ).
5. Альтернативно можна завантажити JSON/CSV, отриманий із законного доступу OAG, і натиснути «Імпортувати графіки».

**Увага:** новий OAG Flight Explorer (`/api/schedules`) та контрактний OAG Schedules (`https://api.oag.com/schedules`) — не тотожні продукти. Не слід вважати, що ключі для одного автоматично відкривають інший.

## Етап I. OAG Delta HTTP Push (обов'язкова для live-дельт активація у OAG)

1. Одержіть Flight Info Alerts entitlement у OAG. Запитайте **HTTP Push (Beta)** через OAG Support — цей варіант не налаштовується повністю самостійно.
2. Повідомте endpoint: `https://ВАШ-WORKER.workers.dev/webhooks/oag`.
3. Попросіть **signed HTTP Push**, HMAC-SHA256, `changeIndicators` та критерії обох напрямків (відправлення і прибуття до/з визначених UK-аеропортів).
4. Узгоджений секрет `whsec_...` збережіть через панель як тип `oag_webhook`; нічого не вносіть у GitHub. Можна замість цього зберегти Cloudflare Secret `OAG_WEBHOOK_SIGNING_KEY`.
5. OAG надсилатиме події; система перевірить HMAC + час + ID, відкине дублікати й збереже зміни. **Dated instance** потрапить у `schedule_exceptions`, **effective schedule** — у `schedule_rules`.
6. На вкладці **«QA і покриття»** перевірте журнал. При пропущених подіях зробіть адресну звірку з OAG Schedules.

## Етап J. Верифікація і поточні ціни

1. Додайте AeroDataBox ключ: вкладка **«Перевірка дат»**, номер рейсу + дата. Підтвердження вказується **тільки після позитивного результату** провайдера.
2. Додайте SerpApi ключ: вкладка **«Ціни й алерти»**, виберіть конкретний маршрут і дату; натисніть «Перевірити актуальні ціни».
3. За бажанням створіть ціновий поріг. Cloudflare Cron перевіряє активні спостереження не частіше разу за добу, якщо вистачає квоти. Досягнення порога з'явиться в журналі, але email наразі не надсилається.
4. Перед бронюванням обов'язково перевірте кінцеву ціну, багаж і доступність безпосередньо у продавця.

## Етап K. Сімейний календар і поїздки

1. Вивантажте з Google Calendar/іншого джерела файл `.ics` для Анни або Саші. У Google Calendar зазвичай: Settings → Calendar → Export; для окремих календарів Export calendar.
2. У вкладці **«Календарі»** виберіть людину, завантажте ICS.
3. Розрахунок кандидатів використовує всі регулярні графіки локально, не звертаючись до авіаційних API.
4. Підтримуються all-day hard blocks, а time-based ICS наразі відображаються для ручного перегляду; для складних повторів потрібен розгорнутий ICS.
5. Для обох дітей оберіть «Обидва»; для канікул — режим «Всі дні» і горизонт до 365 днів. Генератор long-haul — базовий, без підтвердження цін та пересадок.

## Етап L. Робота з GitHub Desktop надалі

1. Я готую код у новій гілці/PR після того, як з'явиться репозиторій (за наявності доступу GitHub connector).
2. У GitHub Desktop → **Fetch origin / Pull origin** для отримання нової версії.
3. Для своїх змін створюйте гілку, комітьте тільки **код**, переглядайте diff і відкривайте PR.
4. GitHub Actions перевіряє Pull Request. Після Merge до `main` Cloudflare автоматично розгортає вебзастосунок.
5. Дані D1 не зберігаються у Git-комітах; у застосунку є `schedule_revisions`, `delta_events`, `price_observations` та можливість експорту CSV. Для повного аварійного відновлення заплануйте backup D1 у Cloudflare Dashboard.

## Приймальний тест

- [ ] GitHub Actions CI показує Success.
- [ ] Cloudflare Workers Builds показує Success.
- [ ] URL відкриває панель; пароль працює.
- [ ] D1 підключена, порожній каталог показує 0, без помилок.
- [ ] API-ключ зберігається, не відображається у списку.
- [ ] STN departures і arrivals створені як дві задачі.
- [ ] AirLabs реально повернув першу сторінку; є точні IATA, дні та час.
- [ ] OAG Schedules повернув періоди startDate/endDate або правильно показав відсутність доступу.
- [ ] Тестовий signed OAG webhook змінює тільки відповідний scheduled instance.
- [ ] Збережені довгострокові графіки видно незалежно від фільтра weekend.
- [ ] Інша дата верифікації не вигадується з регулярного графіка.
- [ ] Ціна SerpApi позначена як пошукова, не як підтверджене бронювання.
- [ ] Анна і Саша можуть імпортувати ICS, all-day blocks впливають на кандидатів.
- [ ] Новий Commit → CI → Cloudflare Deploy працює без командного рядка.

## Public репозиторій і Cloudflare Free

За замовчуванням публікуйте **Public**, але ніколи не комітьте реальні ключі, паролі й дампи реальних даних. Workers Free: 100 000 запитів/день, 10 мс CPU на звичайний запит, 50 D1-запитів на invocation; D1 Free: 5 млн прочитаних і 100 тис. записаних рядків щодня, максимум 500 МБ в одній базі. v8.1 використовує staged commit для AirLabs/OAG і великих delta-пакетів. Перший хмарний deployment і пробний live-тест обов’язкові перед повним імпортом. Див. `docs/PUBLIC_CLOUDFLARE_STUDENT_UA.md`.
